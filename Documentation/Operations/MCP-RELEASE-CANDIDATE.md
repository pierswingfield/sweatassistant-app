## Operating scope and pilot recommendation

The isolated stage endpoint is `https://sweat-mcp-stage.wingfield.tech/mcp`. Runtime flags remain `MCP_ENABLED=true`, `MCP_AUTH_SERVER_ENABLED=true`, **`MCP_PROVIDER_READS_ENABLED=false`**, **`MCP_STAGE_JAB_PROFILE_ONLY=true`**, and no read-window file opt-in in either service. The app is internal-only without a host port; provider background work remains suppressed. Production/dev, public routing, caps and the healthy ChatGPT connection are unchanged.

Six read tools are implemented behind permissions/feature checks. **Only `list_connected_gyms` and `get_automation` are generally available now.** Search/details/bookings/credits are not an ongoing service in this staging mode: passing a temporary acceptance window does not enable a standing provider-read pilot. No booking/payment writes or automation creation are exposed. Claude was explicitly deferred and remains unverified; do not advertise compatibility.

The smallest safe pilot decision is a narrowly described **ChatGPT/two-local-tool** pilot after agreed pilot population/limits, operator monitoring/delivery arrangements and explicit invitation authorization. This is useful for connection inventory and existing automation inspection, not class/account-provider queries. No invitation was sent. A six-tool provider-read pilot instead needs a separately reviewed and authorized standing egress/operating policy and acceptance; do not enable it by dropping profile-only background suppression or silently broadening the expired six-GET window. The original plan's real-Chrome/iOS checks for new UI are retained, not waived. The manifest records remaining evidence boundaries rather than declaring invitation readiness.

The implementation already has persistent common admission: optional account/gym/fleet ceilings of 12/30/60 attempts per minute, concurrency 2/3/4, and optional account/fleet daily ceilings 400/4,000, plus stricter MCP operation/account/gym limits, cooldowns and transport bounds. Those are reviewed implementation limits, not authorization for ongoing JAB traffic. The current gateway still admits only authentication/profile outside the expired, account/session-bound acceptance window. A full read pilot must decide the standing account/gym/path policy, renewal/pagination/metadata needs, approved aggregate limits and operating/alert ownership, reconcile that policy with background suppression, and review/accept the resulting deployment before enabling reads. This packaging task does not implement or authorize that change.

The phone consent-layout check subsequently passed without a submitted decision or new grant. Current device evidence is complete for the selected Safari checks; the remaining full-read-pilot boundary is the [standing-policy proposal](../Workstreams/MCP-STANDING-READ-PILOT.md), its review/operating acceptance and explicit activation/invitation authorization. The post-tag addendum updates evidence only; RC2 artifacts stay immutable.
