# Live API Verification Playbook

> **Read this before making ANY request against a real CodexFit or MarianaTek server** (not a mock, not a fixture). Covers both platforms. This is the safety gate the golden rules in [AGENT_INSTRUCTIONS.md](./AGENT_INSTRUCTIONS.md) point to for "how do I actually do a live check safely."
>
> **Hard rule: no action in this doc executes without the user's explicit per-item go-ahead in that session.** This doc is the *plan* — reading it is not authorization to act on it. An agent picking this up should present the relevant tier's action list and wait for a "go" before making a single live request, exactly as the authoring session did.

---

## 1. Why this exists

Two real third-party services are in play — CodexFit (Psycle London, production) and MarianaTek (JAB Boxing, both a test account and a real stakeholder production account). Prior research sessions already made ~35 live MT requests with zero rate-limit signals (marianatek.md §1G WP-R4) and a live stakeholder capture happened once (§1H) — this doc formalizes that same care into a repeatable checklist so it doesn't rely on one session's memory, and so a cold agent doesn't have to re-derive the safety posture from scratch.

## 2. Non-negotiables (from AGENT_INSTRUCTIONS.md §1, restated for this context)

1. **Never cancel a real paid booking** unless the user has explicitly authorized that specific cancellation, in that session, knowing it may not be reversible (MarianaTek does not return credit on a *penalty* cancel — only a *free-window* cancel is confirmed reversible, per §1H).
2. **Test writes only on the authorized JAB test account** (`aiproscw@gmail.com`, user 60623) unless the user has explicitly named a different account for a specific action.
3. **Reads are lower-risk than writes, but still require a go-ahead** before hitting a real server — even a public, unauthenticated GET. Not because a single GET is dangerous, but because "the agent quietly made outbound calls to a third party" should never be true without the user knowing.
4. **No purchase/payment/checkout, even hypothetically** — this boundary was set explicitly in an earlier session and holds.
5. Anything that surfaces new PII (names, emails, phone numbers, payment metadata, tokens) gets sanitized before it touches the repo — see §5 below for the exact discipline used in the §1H capture.

## 3. Client-fidelity precautions (make requests indistinguishable from the real app)

This automation acts on the **user's own account(s) with their own credentials** — a legitimate personal-use booking assistant, not scraping or impersonating a third party. "Look like an official client" here means: don't get needlessly flagged or throttled by behaving unlike a normal browser/app session, the same courtesy any well-behaved client extends a server.

**Already true today (verified in code, no action needed):**
- `gyms.config.js`'s MarianaTek `clientId` and `redirectUri` are MT's own real web-embed OAuth values (extracted from the live JAB website's own login flow, not invented) — the adapter's login already presents as MT's real web client, not a third-party app.
- CodexFit's adapter already sends the real `origin`/`referer`/`x-organisation` headers the actual Psycle website sends (`gyms.config.js`).
- The MT adapter's headless OAuth (PKCE, cookie jar, CSRF scrape) already replicates the exact multi-step flow a real browser follows (marianatek.md §1B/§1G) — not a shortcut.

**✅ Resolved 2026-07-03.** The user captured real browser DevTools network-tab headers from a live, authenticated `GET /classes` request against the real JAB Boxing widget and provided them directly (not via an agent-driven Chrome navigation). Applied to `gyms.config.js`'s `jab-boxing.headers` (`accept`, `accept-language`, `origin`, `referer`, `user-agent` — all confirmed real, non-personal values) and wired into `providers/marianatek.js`'s `buildHeaders()` (customer-API calls) plus a `browserHeaders()` subset applied to every step of the OAuth login flow (authorize/login-page/token-exchange fetches) and `refreshSession()`. The captured `authorization: Bearer …` value was a live credential and was **not** stored anywhere — discarded after header extraction, per §5's data-handling rule.
- **Deliberately NOT mirrored:** Client-Hints headers (`sec-ch-ua*`, `sec-fetch-*`, `priority`). These are generated by a real browser's actual TLS/HTTP2 negotiation; hand-setting them from a Node server without the matching transport fingerprint is a *more* detectable mismatch than omitting them, and they'd need constant upkeep (the capture's Chrome build number ages daily) to avoid looking stale. `accept`/`accept-language`/`origin`/`referer`/`user-agent` are stable and common to many legitimate non-browser clients too — that's the fidelity bar this project is aiming for, not byte-perfect browser impersonation.
- **A secondary finding from the same capture, not yet acted on:** the real widget's `/classes` request also included `region=48575` and `booking_count_social_proof=true` query params alongside the already-implemented `location`. `region` looks redundant with `location` in this specific request (JAB has one location, already fully scoped) and `booking_count_social_proof` is a UI-only social-proof flag our booking flow has no use for — per the "don't guess the API" rule, neither was added to `fetchTimetable()` without confirming they change response behavior in a way the adapter needs. Noting for a future pass, not treated as an open gap.
- **Verified:** full test suite green after the change (`test-adapters`, `test-marianatek-mock` 12/12 — mock routing is unaffected since it's checked before `buildHeaders()` runs —, `test-poller-upgrade`, `test-calendar-feed`, `test-regression-codexfit-mock`, `test-auth-and-proxy`). Not live-tested against the real JAB API in this pass (that would itself be a live request needing its own go-ahead per Golden Rule 8) — the header values are applied correctly per unit/mock coverage; a live confirmation can piggyback on the next authorized live MT check.

## 4. Rate-limit precautions

- **Budget: ≤40 requests per live-verification session** (the prior WP-R4 session made ~35 with zero rate-limit signal — treat that as the proven-safe ceiling, not a new baseline to push past).
- **Pacing: 200–300ms courtesy delay between paginated/sequential reads** (matches WP-R4's own convention); **300–900ms randomized jitter between any two live writes** (matches the existing `setTimeout(r, 300 + Math.floor(Math.random() * 600))` pattern already used in `poller.js`/`scheduler.js` for real user traffic — reuse it, don't invent a new pacing scheme).
- **No concurrent/parallel bursts** against a live tenant. Sequential only, even though the codebase's own scheduler does controlled concurrent dispatch for real Monday-noon traffic — that's a different, already-load-tested context; a research/verification session should not manufacture burst load against a shared tenant.
- **Stop immediately and report back** on: any `429`, any `Retry-After`/`X-RateLimit-*` header appearing for the first time, or any response that looks like a WAF/bot challenge (unexpected HTML instead of JSON, a CAPTCHA page, a `403` with no prior `401`). Don't retry through it — that's exactly the "identify true positives and pause" behavior a script should have and a scraper wouldn't.

## 5. Data handling (same discipline as the §1H stakeholder capture)

- Real names, emails, phone numbers, DOBs, payment metadata (card last4/expiry, Stripe customer/payment-method ids), bearer/refresh tokens, and any presigned URLs never go into a committed fixture, doc, or test file — replace with `REDACTED_*` placeholders, keep only response *shape* and non-personal values (public business addresses, booleans, counts, spot ids).
- Before committing anything derived from a live capture, `grep` the new/changed files for the account's real name/email/phone and any token string — the §1H handoff's own post-capture check is the model to follow.
- Raw capture files (browser network-tab dumps, curl transcripts with real tokens) live **outside the repo** (session scratchpad or the user's own machine), never staged.

## 7. How to run a Tier-0/1/2 action, step by step (for whoever executes this)

1. Read this doc + the latest PROGRESS.md handoff first — confirm nothing has changed that invalidates a "safe" classification here (e.g. a new rate-limit signal reported since this was written).
2. Present the specific numbered action(s) (e.g. "T0-1", "T1-1") to the user and get an explicit go-ahead **for that action specifically** — not a blanket "yes to the playbook."
3. Execute with the pacing/budget rules in §4. Log status codes and response shapes as you go (not just the final result) — if something looks like throttling, stop per §4 before continuing to the next call.
4. Sanitize per §5 before writing anything to a fixture, doc, or commit.
5. Update the relevant Open Question row in PROGRESS.md to ✅ (or note partial progress) and append a Handoff Log entry, same as any other WP.
