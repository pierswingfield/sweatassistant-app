# Team welcome routing investigation — 2026-11-13

The owner reported that the installed iPhone app opened Home after finishing setup. Remote read-only evidence supplied by the parent showed the setup DELETE returned 200 and the Team invite preview GET returned 200. Neither establishes which panel was visible or the preview's response state. The parent separately checked that the account was not already a Team member and had no join request.

A production-built local fixture was tested in the user's Chrome via CDP using a disposable database, an account with zero gyms, ordinary root launch after clearing localStorage, sessionStorage, IndexedDB, CacheStorage and service workers, and non-reduced motion. A simulated standalone media query was applied before finishing; this was **not** an iOS installation or WebKit test.

`routing-cdp.cjs` reported:

```
BEFORE {"path":"/","hasPending":true,"signupMarked":true,"standalone":true}
AFTER {"path":"/teams","visibleHome":false,"visibleTeams":true,"visibleWelcome":true,...}
TEAM_RESPONSES [onboarding DELETE 200, invite preview GET 200]
PASS production bundle: visible Team welcome after no-storage standalone-mode setup
```

The history trace was `/` → `/t/[redacted]` → `/teams`. [Visible welcome](visible-welcome.png). A second local run instrumented the same finishing transition for 12 seconds and observed the invite preview response `myRequestStatus: none`, Teams panel `display: flex`, Home panel `display: none`, and no later history, popstate, visibility or pageshow events. [Visible after 12 seconds](visible-after-12s.png).

The iPhone-reported Home result was **not reproduced**. In the code, the pending server row is deleted before navigation and the local invite is consumed before preview rendering, so interruption or another navigation during this interval is a possible failure mode; it is not established as the cause of the observed iPhone result. The server also deliberately directs existing members to their Team dashboard, but the parent’s account check rules that branch out for this case. Determining the actual native path requires further device evidence.

The parent’s [scrubbed production request trace](remote-request-trace.json) records a successful setup DELETE followed by an invite preview GET 200 for the owner’s attempt, with no 401 or 403 in the inspected interval. This establishes that the preview request reached the server; it does not establish the response state, visible panel, or whether later navigation occurred. It does not support the hypothesis that the invite was lost before the preview request.

A follow-up Chrome run used an iPhone Safari user agent, `navigator.standalone = true`, 393 × 852 CSS-pixel viewport at DPR 3, and CDP touchStart/touchEnd at the visible finish button’s center (x 206, y 817). Twelve seconds later the URL was `/teams`, Teams was visible, Home hidden, and the request-to-join welcome was visible; the setup DELETE and invite preview returned 200. [Mobile screenshot](mobile-trusted-touch-welcome.png) is 1179 × 2556 pixels. The earlier `visible-after-12s.png` was captured after the emulation session ended and is desktop-sized; it is not mobile-layout evidence.

Separately, the iPhone 15 Pro standalone WebKit emulator opened the production fixture with a fresh Team signup, cleared both storage areas and browser caches, logged in at ordinary root and used its touch tool for setup. After finishing, `/teams` showed the invitation and Home was hidden; it remained visible on a later check. Debug logs contained no page exceptions or network failures. They did record no-gym 409 responses for bookings, waitlists, profile, credits and eligibility, plus a timetable prefetch error. This is WebKit emulation, not the owner's physical iPhone.
