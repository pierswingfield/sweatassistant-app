# Proposed bounded JAB provider-read acceptance

Prepared for review only. Provider-backed MCP reads remain disabled; this document is not authorization to enable them. Current authorization covers dedicated JAB authentication/profile linking only. A candidate containing all six registered read tools can retain the provider-read flag off; it must describe only the two local tools as currently available.

## Reviewable run

Use only the existing dedicated staging JAB account and its existing session. Keep stage profile-only mode enabled so scheduler, poller, calendar and gym-link history work stay suppressed. Do not modify production/dev, expose another route, access class history, buy credits, create/cancel bookings, or create/change automations. Do not broaden the existing user's OAuth grant: it intentionally lacks schedule permission. Full schedule-tool acceptance would need explicit additional scope consent or a separately supported test-account session approved for that purpose; no silent grant expansion or token fabrication.

A future reviewed gateway mode must admit only HTTPS GETs on the exact configured JAB host, canonical paths and bounded query keys: `/api/customer/v1/me/credits`; `/api/customer/v1/me/reservations?is_upcoming=true&page_size=100`; `/api/customer/v1/classes` with an explicitly selected one-day min/max date and page size 100; and `/api/customer/v1/classes/ID` for one ID returned by that search. Permit at most six upstream GETs in the whole acceptance window, one in flight, maximum 120 seconds, the existing 12-second MCP deadline, 15-second gateway deadline and 1 MiB gateway response limit. Keep the existing common account/gym/fleet budgets; stop rather than retry on 401, 429, timeout, unexpected pagination or exhausted budget. No refresh-token exchange is allowed. A restart must not reset an active acceptance allowance; expire the window before rollout/restart.

Run the four provider tools sequentially once each: one-day `search_classes` (limit 1), `get_class_details` for one returned class, `get_my_bookings` (limit 1), and `get_credits`. Return only redacted counts, IDs and statuses in evidence, not raw records. The booking adapter may request a class-list enrichment for reservation dates; deny any date outside the approved one-day window. That enrichment is best effort and may fail without hiding the booking response. Never follow arbitrary pagination URLs or widen date bounds to obtain a passing test. Restore provider reads off immediately after the window. Capture bounded per-client/tool admission/provider-attempt counters and verify no writes/history/background calls.

## Required before enabling

Implement and independently review the separate disabled-by-default read-window policy, durable aggregate cap and cancellation behavior. Exercise exact adapter-to-gateway fixture calls without network: accepted canonical GETs, rejected extra/duplicate/encoded query variants, wrong hosts/methods/IDs/dates, paging outside the window, cap exhaustion, expiry, restart behavior, 401 and 429 without outbound reauthentication. Current deployed policy intentionally rejects these provider reads; existing profile-only gateway tests do not establish the proposed mode. Obtain explicit approval of the bounded read scope and any necessary OAuth scope consent only after this concrete implementation passes review. No new provider policy or runtime flag has been enabled in this pass.
