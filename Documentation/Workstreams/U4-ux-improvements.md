> **U4-16 plan (2026-09-29).**
> **Basis (verified in code).** Today the feed has one flag, `includeTentative`, which switches waitlist AND Auto-Book rows on together (default off), and one `alarm` dropdown (`none|2h|penalty|both`) that adds VALARMs to confirmed classes only (2 h and 12 h before start). Calendar is an ACCOUNT-scoped setting (`calendar` key).
> **Settings model (all inside the existing account-scoped `calendar` key, so `ACCOUNT_SCOPED_SETTING_KEYS` is unchanged).** `includeWaitlists`, `includeAutoBook`, `remindBookingWindow`, `reminders: { twoHour, cancelWindow }`. Booked classes are always included. **Migration is read-time, non-destructive** (`normalizeCalendarPrefs` in `server/calendar-prefs.js`): a missing new key falls back to the legacy value (`includeTentative` sets both include flags; `alarm` maps to the two reminder checkboxes), so an existing subscriber's feed is byte-for-byte the same set of events. The legacy keys are dropped only when the user next saves. `remindBookingWindow` defaults OFF so nobody gains events they did not ask for. The `/enable` route still accepts the legacy `includeTentative`/`alarm` body.
> **VALARM targeting.** Booked: 2 h and/or 12 h (free-cancellation window) per checkboxes. Booking-window-opens events: one 15-minute alarm, nothing else. Waitlist and Auto-Book events: never any VALARM.
> **Booking-window events.** Generated at serialisation time (no DB rows) for every linked gym whose `bookingWindow.kind` is `rolling-weekly` (read from `gyms.config`, never a gym id), for the next 4 release instants, title `<shortName> booking window opens`, deterministic UID `psycle-<user>-bw-<gym>-<YYYYMMDD>@host`, 15-minute duration. The UI only shows the option when a linked gym is weekly (`/api/calendar/status` returns `weeklyGyms`).
> **UI.** One pane `calendar`, card order: feed on/off (+Refresh), Include, Reminders, Add to calendar (Apple, Google, Copy link, inline logo SVGs; shown while the feed is on). Corrected 2026-09-29: it was first built as a separate pane and nav entry. Only `styles.css` is touched for styling; light/dark parity.
> **Nav.** About first, Account last; per-gym entries now anchor before Account.
> **Tests.** `server/test-calendar-prefs.js` (include flags, targeted VALARMs, window-event generation and UID stability, legacy migration); existing calendar suites must stay green.

> **U4-17 plan (2026-09-29; agreed design, not yet implemented).**
>
> **Basis (verified in code).** `client/src/ui/onboarding.js` currently runs the seven-step sequence `intro → install → login → gyms → notifications → spotmaps → calendar` (`ONBOARDING_VERSION = '3'`). The intro leads with “Unofficial client”, the login/storage reassurance says credentials are stored on a “private server”, and notifications, spot maps and calendar each have their own onboarding step. `client/index.html` repeats “private server” wording in the recovery and Settings privacy copy. The calendar experience and its requested actions/icons are being reworked under U4-16. Preferred Spot Maps are edited through overlays in `settings.js`; the redesign must ensure only one active editor/modal is present and that its summary is refreshed after save or gym changes.
>
> **Core flow.** Keep a guided full-screen flow that is resumable across launches and has consistent Back controls. The welcome screen must use the exact title **“Welcome to Sweat Assistant!”**, shared About content, and **Log In** / **Create Account** actions. Keep the core path short: account access, gym connection, then the feature roll-up. Use gym-configured names, labels and branding wherever a gym is shown. After the first gym connects, collapse the second-gym form into a clear **Connect another gym** button; do not force a second gym. Preserve a no-gym account path and allow a user to resume after partial completion.
>
> **Security copy.** All onboarding and Settings copy covered by this item must say that gym login credentials are **encrypted and stored in a secure private cloud**. It must also explain that stored data can be deleted from Settings. Do not describe the storage as a private server, and do not imply that a gym credential is the Sweat Assistant account credential.
>
> **Feature roll-up.** After gym linking, show one optional screen with three independent setup cards:
>
> 1. **Notifications** — “Tap to enable”, marked **Recommended**. Explain that push alerts cover booking, upgrade and cancellation updates; handle unsupported browsers and denied permission without trapping the user.
> 2. **Calendar** — use the U4-16 Calendar Sync language, actions and icons (including Apple Calendar, Google Calendar and Copy link where available). The card should describe the live feed plainly and route into the same enable flow as Settings.
> 3. **Preferred Spot Maps** — describe the shared map in one or two sentences: the same preferred spots power **Auto-Book**, **Quick-Book** and **Auto-Upgrade**. Present maps grouped **Gym → location → studio**. Fix stacked duplicate overlays and stale summaries while making the editor re-enterable from Settings.
>
> Each card can be completed independently. The bottom action reads **Set up later** while any card is incomplete. When all three are complete, change it to **Continue to timetable** (or equivalent direct wording) and take the user to the timetable. Settings remains the permanent re-entry point. Define and preserve states for no gym, partial completion, permission denied, unsupported notification capability, Back, resume and a user who completes setup from Settings before returning to onboarding.
>
> **Tone and motion.** Lead with the user’s outcome and the next action. Use short, warm, direct sentences; explain why a permission or credential is needed at the point of request; avoid implementation claims and broad privacy promises. Add subtle motion only where it confirms progress or completion (for example, a card check state or the second-gym form collapsing into its button). Keep transitions brief and cancellable. Every motion treatment needs a `prefers-reduced-motion` path that removes movement while preserving state, focus and meaning.
>
> **Acceptance criteria.** The welcome title, shared About content, Log In/Create Account actions, Back behaviour and resumability are present and keyboard/touch usable. Gym labels come from gym configuration. The second-gym form collapses after the first successful connection. The security copy uses “encrypted and stored in a secure private cloud” plus data deletion. The roll-up has exactly three independent cards, the combined spot-map explanation, the required incomplete/complete bottom labels, and no forced setup. Preferred Spot Maps show the Gym → location → studio hierarchy with one active editor and fresh saved state. Calendar actions and copy align with U4-16. Light and dark themes, mobile width, no-gym, partial, denied and unsupported states are covered.
>
> **Verification required before marking done.** Follow [AGENT_PROTOCOL.md](AGENT_PROTOCOL.md): inspect the changed code, then use one real Chrome tab at approximately 402px and desktop width in light and dark themes. Clear service-worker/CacheStorage, IndexedDB and reload before checking. Capture evidence for a new account, resume/Back, first and optional second gym, each roll-up card, permission denial/unsupported notifications, calendar actions, spot-map hierarchy/modal cleanup and the final timetable hand-off. Run the relevant test/build command and record its actual result. This item does not authorise launch or deployment.
