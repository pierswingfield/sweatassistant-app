Two consequences beyond the isolation work already done: (1) **copy and design must be entirely gym-neutral** — the About pane shipping "Psycle London / CodexFit / (Monday 12PM)" to a JAB user showed the UI still assumes a single tenant in prose even where the logic no longer does; (2) **all linked gyms must appear in parallel in every view**, filterable by gym in the timetable. This **resolves Q4** ("build a merged all-gyms view?") as yes, and it is a larger change than it sounds: provider ids are unique only within a gym, so a merged list has real id collisions; theming and capability gating both become **per-row** rather than per-document; and the server needs a fan-out that degrades per gym instead of failing the whole request. Tracked as P1/P2 in OUTSTANDING.md.

- **2026-09-02 · D7 · Eligibility is a first-class question, and must never be derived from credits.** Prompted by the stakeholder pointing out the JAB test account has no membership, so "cannot book" was in fact correct — reached via the wrong input. `metered` and `creditPurchase` do not answer "can this account book here at all", and a membership gym needs that answer explicitly. Credit arithmetic must not be repurposed to stand in for it (it warned identically for a JAB user *with* a valid membership, which is why it was removed). `providers/marianatek.js getMemberships()` already exists and is wired to no route — that is the seam. Tracked as J in OUTSTANDING.md.

- **2026-08-31 · D5 · Gym credentials must never be an account-recovery factor.** The first recovery implementation proved identity by making the user sign in to a linked gym. Rejected by the stakeholder. It re-coupled the Sweat Assistant account to the gym — cancel the membership and the account becomes unrecoverable — and it silently promoted the gym password to a permanent master key for the SA account, inheriting both the gym's password rules and the gym's security posture, neither of which we control. Removed (endpoints, client flow and tests; a regression test asserts they stay removed). Replacement mechanism is undecided — candidates and trade-offs in BACKLOG.md. **Settled independently of that choice:** a successful recovery resets **all** stored gym credentials (`db.resetGymCredentials()`); links, queues, spot maps and priority tiers survive and the user re-authenticates each gym. With no gym in the proof, the earlier "keep the gym we just verified" carve-out no longer applies.

- **2026-08-31 · D4 · A Sweat Assistant account gets its own identity.** Decided by the stakeholder. The SA login is no longer "whichever gym you first signed in with" — it is a first-class identity that *holds* N gym credentials, so cancelling a Psycle membership cannot cost you JAB access. Consequences for WP-C2: signup/login needs an SA-native credential path separate from any gym's; `users` keeps the SA identity while `user_gyms` (already built, WP-D3) keeps the per-gym auth; existing single-gym users must migrate without a forced re-login (their current gym email/password becomes the SA identity by default, with the gym credential copied into `user_gyms` — which D3 already did).

- **2026-07-01 · D3 · JAB v1 scope = full parity, purchases de-scopable.** MT/JAB is membership-based with no confirmed purchase API and no bookmarks API; those surface as capability-flagged "unsupported" states, not blockers.
- **2026-07-01 · D2 · Umbrella brand = "Sweat Assistant"** with per-gym theming. Supersedes prior "Psycle Assistant" single-gym name for multi-gym copy/manifest/config.
- **2026-07-01 · D1 · Membership model = multiple gyms per account** (`user_gyms` join table, gym switcher, merged/switchable timetable). Largest schema change; drives Phase 2.
- **2026-07-01 · Config source of truth = static `server/gyms.config.js`** registry (code + env secrets) with a thin `gyms` DB table for referential integrity. Revisit if self-service gym onboarding is needed.
